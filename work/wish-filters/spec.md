# Пожелания как фильтры

Ветка `feat/wish-filters` от `feat/hotel-agent-mvp`.

## Решения пользователя (2026-10-29)

- Удаление фильтра сразу пересчитывает выдачу.
- Чипы на главной добавляют фильтр, поиск запускается кнопкой отправки.
- Фильтры живут в контракте API: бэкенд принимает активный набор и возвращает разобранный.

## Модель

Фильтр — одно понятое условие: `kind` (`wish`, `location`, `dates`, `guests`), `label` словами
пользователя для `wish` и `location`, структурные поля `check_in`/`check_out`/`adults` для
остальных, `key` — ключ характеристики, когда он известен.

Источник истины после поиска — `parsed` в снимке выдачи: `intents[].source_text` уже включает
nearby/facility/spatial запросы, плюс `location_hint`, даты и гостей.

## Поток

1. Фронт всегда шлёт `filters` — то, что пользователь видит над полем ввода.
2. Бэкенд собирает из набора текст запроса и подставляет его вместо `previous_search_query`
   в контекст диалога, поэтому удалённое условие исчезает и из нового запроса.
3. Пустое сообщение с непустым набором — это правка фильтров: без обращения к роутингу,
   сразу поиск по собранному тексту, пользовательская реплика в чат не пишется.
4. Ответ возвращает `filters`, разобранные из новой выдачи; фронт заменяет ими свой набор.

## Шаги

1. Контракт: `ChatFilter`, `ChatRequest.filters`, `Conversation.filters`, пустое `message`.
2. Бэкенд: `domain/filters.py`, `application/chat_filters.py`, `Chat.send(filters=...)`,
   сохранение ответа без реплики пользователя, схемы и роутер.
3. Тесты бэкенда: сборка запроса из набора, удаление условия, правка без сообщения.
4. Фронт: фича `search-filters`, панель над полем ввода, чипы главной добавляют фильтр,
   отправка и правка через `useConversation`, словари ru/en.
5. Проверки: `npm run verify`, `ruff`, `mypy`, `pytest tests/unit`, живой прогон на стенде.
