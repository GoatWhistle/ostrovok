# Кабинет отельера и оповещения

Ветка `feat/hotelier-cabinet`, ответвлена от `feat/hotel-agent-mvp` на коммите `1d56ee9`,
работа велась в `.claude/worktrees/hotelier`. Бэкенд целиком, без фронтенда.

## Зачем это делалось

На стенде 28 октября кабинет отельера существовал как таблица, а не как рабочий контур:
**80 321 открытый вопрос при одном отвеченном** (три характеристики × ~26 780 отелей — декартово
произведение в `CANDIDATES`), и ни одного способа узнать, что с отелем что-то произошло. Отельеру
нечего было открыть, кроме списка, который он никогда не разберёт.

### Восемь видов оповещений

`question_opened`, `answer_accepted`, `answer_needs_detail`, `fact_changed`, `fact_expiring`,
`conflict_opened`, `conflict_resolved`, `search_demand`. Срочность `action` или `info` выводится из
смысла: перепроверка, опровергнувшая подтверждённое отельером значение, требует действия, та же
перепроверка поверх расчёта — нет (`change_severity`).

В базе нет текста: вид события, ссылки и `payload` из чисел. Фразу собирает клиент — язык кабинета
не оседает в данных.

### Спрос как источник приоритета

Снимки выдачи уже лежат в `chat_conversations.search_snapshot` вместе с качеством совпадения по
каждому условию. Отсюда считается, сколько раз незнание характеристики не дало ответить на живой
запрос (`adapters/db/hotelier_demand.py`), и это решает, о чём спрашивать
(`worth_asking`) и в каком порядке (`question_priority`).

### Один следующий шаг

`first_attention`: сначала спорное значение, затем самый весомый вопрос, затем подтверждение
истекающего ответа отельера. Это поле `next_action` в сводке.

## Границы

- На стенде этого кода нет: образ не пересобирался, чтобы не сломать работу параллельных сессий.
  Проверено дисковыми базами с теми же миграциями, не живым стендом.
- Фронтенда нет по условию задачи. `frontend/src/shared/api/schema.gen.ts` не перегенерирован:
  после слияния нужен `cd frontend && npm run api:types`.
- Спрос существует только по запросам, прошедшим через чат, и считается полным проходом по
  разговорам за окно наблюдения. На демо-объёме дешевле отдельного учёта.
- Входа и прав нет, как и раньше: кабинет открывается по адресу.
- Внешние каналы доставки (почта, пуш) не делались: лента в кабинете плюс счётчики непрочитанного.
- Оповещения о собственном подтверждении или исправлении факта не создаются намеренно; создаются
  только о возникшем или закрытом из-за правки противоречии.

## Что осталось за рамками

- Вопросы по причинам `conflict`, `stale` и `low_confidence` планировщик не заводит: эти случаи
  закрыты оповещениями. Если понадобится именно вопрос, нужен ещё один источник кандидатов.
- Поток оповещений (SSE) не делался: лента отдаётся страницами с курсором.
- `make notify-hoteliers` запускается вручную; планировщика в проекте нет.
