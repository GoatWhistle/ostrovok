# Кабинет отельера и оповещения

Ветка `feat/hotelier-cabinet`, ответвлена от `feat/hotel-agent-mvp` на коммите `1d56ee9`,
работа велась в `.claude/worktrees/hotelier`. Бэкенд целиком, без фронтенда.

## Зачем это делалось

На стенде 28 октября кабинет отельера существовал как таблица, а не как рабочий контур:
**80 321 открытый вопрос при одном отвеченном** (три характеристики × ~26 780 отелей — декартово
произведение в `CANDIDATES`), и ни одного способа узнать, что с отелем что-то произошло. Отельеру
нечего было открыть, кроме списка, который он никогда не разберёт.

#### Разборка накопленной очереди

Приоритет по спросу ничего не меняет, если очередь уже занята: старый обход занял все 80 322 пары
«отель × характеристика», поэтому планировщик не находит кандидатов. `PruneHotelierQuestions`
(`make prune-questions`, по умолчанию только печатает) откладывает открытые вопросы, которых не
спрашивал ни один живой запрос, и возвращает в работу отложенные, на которые спрос появился.
Отвеченные не трогает. Замер по стенду 28 октября, только чтение:

| Срез | Открытых | Пар со спросом | Отложить | Вернуть | Станет открытых |
|---|---|---|---|---|---|
| Сочи | 301 | 46 | 284 | 27 | 44 |
| Все регионы | 1 764 | 258 | 1 659 | 151 | 256 |

94 % открытых вопросов по Сочи никому не понадобились, а 27 нужных лежали в отложенных — система
спрятала именно то, что спрашивают.

## Восемь видов оповещений

`question_opened`, `answer_accepted`, `answer_needs_detail`, `fact_changed`, `fact_expiring`,
`conflict_opened`, `conflict_resolved`, `search_demand`. Срочность `action` или `info` выводится из
смысла: перепроверка, опровергнувшая подтверждённое отельером значение, требует действия, та же
перепроверка поверх расчёта — нет (`change_severity`).

В базе нет текста: вид события, ссылки и `payload` из чисел. Фразу собирает клиент — язык кабинета
не оседает в данных.

### Спрос как источник приоритета

Снимки выдачи уже лежат в `chat_conversations.search_snapshot` вместе с качеством совпадения по
каждому условию. Отсюда считается, сколько раз незнание характеристики не дало ответить на живой
запрос (`adapters/db/hotelier_demand.py`), и это решает, о чём спрашивать
(`worth_asking`) и в каком порядке (`question_priority`).

### Один следующий шаг

`first_attention`: сначала спорное значение, затем самый весомый вопрос, затем подтверждение
истекающего ответа отельера. Это поле `next_action` в сводке.

## Эндпоинты

```
GET  /api/v1/hotelier/{hotel_id}/overview
GET  /api/v1/hotelier/{hotel_id}/questions?status=open
GET  /api/v1/hotelier/{hotel_id}/notifications?unread_only&cursor&limit
POST /api/v1/hotelier/{hotel_id}/notifications/read
POST /api/v1/hotelier/{hotel_id}/answers
POST /api/v1/hotelier/{hotel_id}/facts
```

Последний закрывает дыру кабинета: отельер видел «неизвестно», но сказать значение сам не мог —
только ответить на заданный вопрос или исправить существующий факт.

## Отдельный стенд

Проверка шла не на общем стенде, а на своём: `COMPOSE_PROJECT_NAME=hotelier`, PostgreSQL на 5442,
бэкенд на 8010, собственный том данных.

```bash
COMPOSE_PROJECT_NAME=hotelier TAG=latest docker buildx bake backend
COMPOSE_PROJECT_NAME=hotelier POSTGRES_PORT=5442 BACKEND_PORT=8010 \
  docker compose up -d --wait db migrate backend
cd backend && DATABASE_URL=postgresql://hotel:hotel@localhost:5442/hotel \
  CHARACTERISTICS_DIR=../characteristics SEED_DIR=../data/seed \
  uv run hotel-agent ingest --region sochi --from ../data/seed/sochi
# затем precompute той же командой
```

Важно: `make seed` и `make precompute` подставляют порт из `.env`, то есть пойдут в общую базу.
Для своего стенда нужен явный `DATABASE_URL`, как выше.

Результат прогона петли и измеренная граница — в
[доказательствах](../../docs/evidence.md#петля-запрос--вопрос--ответ-на-отдельном-стенде-28-октября-2026).

## Как включить на стенде

Кода в образе стенда нет. Порядок включения:

1. Слить ветку `feat/hotelier-cabinet`.
2. `docker compose run --rm migrate` — применит `20261028120000_hotelier_notifications`; миграция
   только создаёт таблицу, существующих не меняет.
3. Пересобрать и поднять образ бэкенда (`docker buildx bake backend`, затем `docker compose up -d backend`).
4. `make prune-questions` — посмотреть числа; `APPLY=1 make prune-questions` — разобрать очередь.
5. `make notify-hoteliers` — поставить напоминания о сроках и спросе.
6. `cd frontend && npm run api:types` — перегенерировать `schema.gen.ts` под новый контракт.

Проверить вживую:

```bash
curl -s localhost:8000/api/v1/hotelier/<id>/overview | jq '.coverage, .next_action, .appearances'
curl -s localhost:8000/api/v1/hotelier/<id>/notifications | jq '.unread, .items[0]'
```

## Границы

- На стенде этого кода нет: образ не пересобирался, чтобы не сломать работу параллельных сессий.
  Проверено одноразовыми базами с теми же миграциями, не живым стендом.
- В общую базу стенда ничего не писалось: миграцию применить не дала политика среды
  («Modify Shared Resources»), обходить её я не стал. Поэтому числа разборки очереди по общей базе —
  замер запросом на чтение; всё остальное проверено на отдельном стенде.
- Ответ отельера пока не меняет ту же выдачу: запрос спрашивает под производным ключом, ответ
  лежит под именем характеристики. Граница измерена и описана в
  [ограничениях](../../docs/limitations.md#ответ-отельера-не-попадает-в-ту-же-выдачу).
- Предпросмотр очистки для сдачи (`strip-ai.sh` без `--apply`) теперь даёт «no AI traces, no broken
  links»: внутренний путь в `docs/design-decisions.md` заменён на нейтральную формулировку.
  Остались пять срабатываний стилевой проверки в чужих текстах — все ложные, на словах
  «уникальных», «позволяет оценить», «не является источником».
- Фронтенда нет по условию задачи. `frontend/src/shared/api/schema.gen.ts` не перегенерирован:
  после слияния нужен `cd frontend && npm run api:types`.
- Спрос существует только по запросам, прошедшим через чат, и считается полным проходом по
  разговорам за окно наблюдения. На демо-объёме дешевле отдельного учёта.
- Входа и прав нет, как и раньше: кабинет открывается по адресу.
- Внешние каналы доставки (почта, пуш) не делались: лента в кабинете плюс счётчики непрочитанного.
- Оповещения о собственном подтверждении или исправлении факта не создаются намеренно; создаются
  только о возникшем или закрытом из-за правки противоречии.

## Что осталось за рамками

- Вопросы по причинам `conflict`, `stale` и `low_confidence` планировщик не заводит: эти случаи
  закрыты оповещениями. Если понадобится именно вопрос, нужен ещё один источник кандидатов.
- Поток оповещений (SSE) не делался: лента отдаётся страницами с курсором.
- `make notify-hoteliers` запускается вручную; планировщика в проекте нет.
