# Требования и оценивание

Источник: [TASK.md](TASK.md) — ТЗ дословно (веб-страница без страниц, ссылки идут на разделы);
ответы организаторов — [QA.md](QA.md); правила сдачи — [PLATFORM.md](PLATFORM.md). Здесь — пересказ
требований организаторов с указанием раздела ТЗ. Наши идеи, предложения и допущения помечены
«**наше:**» и требованиями не являются.

## Задача — раздел «Формулировка задания»

- Разработать прототип агентной системы для Островка: собирать уникальные характеристики отелей и
  номеров из открытых данных и у отельеров, систематизировать, хранить и показывать пользователю
  [раздел «Формулировка задания»].
- Для путешественника, который ищет отель по своим словам; для Островка, которому нужно знать об
  отелях больше, чем в карточках; для отельера, который хочет ответить на вопросы один раз
  [раздел «User Story»].
- Результат — работающий прототип для набора отелей выбранного региона, в котором пользователь
  находит отель по собранным системой характеристикам [раздел «Ожидаемый результат»].
- Ни API, ни MCP-серверов, ни данных Островка не дают: список отелей, данные, инструменты агентов,
  логику и интерфейс собираем сами из открытых источников — OpenStreetMap, карты высот, публичные
  датасеты и API [раздел «Формулировка задания»].
- Технологии, модели и архитектура не ограничены; состав характеристик, источники, распределение
  работы между агентами и выбор «считать по данным или спросить отельера» — на нас
  [раздел «User Story»].
- Основная сложность — не придумать характеристику, а достоверно её получить: откуда агент её
  берёт, насколько уверен, как проверить и когда она устареет. Агент, который просит LLM «угадать,
  есть ли вид на море», решением не считается [раздел «Формулировка задания»].

## Обязательные требования — раздел «Основные задачи»

| # | Требование | Раздел ТЗ | Как проверим |
|---|---|---|---|
| R1 | Сбор характеристик: агент сам решает, какие источники и инструменты нужны для конкретной характеристики, и получает её значение. Хотя бы одна характеристика вычисляется по геоданным, а не находится в тексте | «Основные задачи», п. 1 | Факт с методом расчёта по DEM и footprint'ам OSM в карточке отеля; шаг маршрута для жюри |
| R2 | Диалог с отельером: если данных не хватает, агент задаёт вопрос, принимает ответ в свободной форме и раскладывает его по нужным полям. Отельера можно имитировать | «Основные задачи», п. 2 | Вопрос, сгенерированный по пропуску; ответ свободным текстом превращается в факт с цитатой |
| R3 | Хранение и достоверность: у каждого значения есть источник, уверенность и дата получения. Противоречия источников система замечает и разбирается с ними | «Основные задачи», п. 3 | Поля источника, уверенности и даты в карточке; запись о конфликте и правило разрешения |
| R4 | Расширяемость: новую характеристику можно добавить без переписывания системы, например описав её текстом | «Основные задачи», п. 4 | Новая характеристика описанием, без правки кода; поиск по ней работает |
| R5 | Поиск по запросу: пользователь описывает своими словами, что ему важно («тихий номер с видом на закат недалеко от моря»), и получает подходящие отели | «Основные задачи», п. 5 | Основной сценарий на стенде от сообщения в чате до выдачи |

## Требования к результату — раздел «Ожидаемый результат»

| # | Требование | Раздел ТЗ | Как проверим |
|---|---|---|---|
| R6 | Прототип работает для набора отелей одного выбранного региона; рекомендовано сосредоточиться на одном регионе, а не охватывать несколько поверхностно | «Ожидаемый результат» | Регион заявлен, глубина по нему показана |
| R7 | Проект запускается по инструкции из README | «Ожидаемый результат» | Запуск из чистого клона по README |
| R8 | Без многочасовой загрузки данных: заранее собранные демо-данные лежат в репозитории | «Ожидаемый результат» | Демо-данные в репозитории, время подъёма стенда измерено |
| R9 | Если нужен ключ LLM — это описано в README и приложен `.env.example` | «Ожидаемый результат» | README и `.env.example` в репозитории |

## Необязательные пункты и бонусы — раздел «Дополнительные задачи»

| # | Пункт | Раздел ТЗ | Что даёт |
|---|---|---|---|
| O1 | Объяснение выбора: почему отель подходит под запрос и в чём не дотягивает («вид на закат есть, но только с 5-го этажа») | «Дополнительные задачи», п. 1 | Веса и баллы не опубликованы |
| O2 | Сравнение нескольких отелей или номеров по собранным характеристикам | «Дополнительные задачи», п. 2 | Веса и баллы не опубликованы |
| O3 | Кабинет отельера: видит, что система узнала, подтверждает или исправляет значения, отвечает на вопросы агента | «Дополнительные задачи», п. 3 | Веса и баллы не опубликованы |
| O4 | Актуализация: система повторно проверяет устаревшие данные и реагирует на изменения, например рядом построили дом и закрыли вид | «Дополнительные задачи», п. 4 | Веса и баллы не опубликованы |
| O5 | Метрики качества: собственная размеченная выборка и замеры — точность характеристик, покрытие, доля вопросов к отельеру | «Дополнительные задачи», п. 5 | Веса и баллы не опубликованы |

## Примеры характеристик для вдохновения — раздел «Примеры для вдохновения»

ТЗ называет это примерами, а не обязательным списком: «чем больше своих идей и proof of concept вы
придумаете, тем лучше».

| Группа | Примеры ТЗ |
|---|---|
| Вычислить по геоданным | Вид на закат или достопримечательность (DEM SRTM или Copernicus, высоты зданий из OSM, прямая видимость, этаж, сторона фасада, положение солнца по датам); вид на море или горы с какого этажа; тишина (дороги и их класс, железная дорога, бары и клубы, аэропорт, открытые карты шума для Европы); реальная доступность по пешему маршруту с перепадом высот и переходом трассы; что работает ночью по `opening_hours`; для семей с детьми (площадки, пешеходные улицы, детская больница); на машине (подъезд, пешеходная зона, парковка, зарядки для электромобилей); дорога из аэропорта по расписаниям GTFS |
| Найти в других открытых источниках | Погода и климат по месяцам (Open-Meteo); качество воздуха (OpenAQ); связь для удалённой работы (OpenCellID); стройки и мероприятия рядом с городских порталов открытых данных; история здания (Wikidata и Википедия); фото с геометками (Wikimedia Commons, панорамы Mapillary) |
| Узнать у отельера | Вопрос отельеру со свободным ответом и раскладкой по полям; размещение с питомцами (кого и до какого веса, цена, площадка для выгула) |

## Критерии жюри — на странице ТЗ нет

Критериев, весов и баллов опубликованная страница трека не содержит — **без весов**. Пока критерии
не получены, приоритет задаётся порядком ТЗ: пять основных задач раньше пяти дополнительных.
Вопрос открыт в [open-questions.md](../context/open-questions.md).

## Что ТЗ требует от документации — раздел «Ожидаемый результат»

- Инструкция запуска в README [раздел «Ожидаемый результат»].
- Описание необходимости ключа LLM и `.env.example` [раздел «Ожидаемый результат»].
- Для каждого значения — источник, уверенность и дата получения; как значение проверить и когда оно
  устареет [разделы «Формулировка задания», «Основные задачи», п. 3].

## Тайминг по дням — на странице ТЗ нет

Расписания, дедлайна и регламента защиты страница трека не содержит. Дедлайн и правила сдачи
фиксируются в [PLATFORM.md](PLATFORM.md), расписание — в [event.md](event.md), как только источник
получен.

## Контрольные точки команды

**Наше:** внутренние рубежи относительно дедлайна T из [PLATFORM.md](PLATFORM.md).

| Когда | Что готово |
|---|---|
| Конец дня 1 | P0-сценарий проходит от начала до конца на настоящем бэкенде с засеянными демо-данными; название и токены выбраны |
| T − 24 ч | Заморозка функций P0 и P1, замеры прогнаны, план презентации с настоящими числами |
| T − 8 ч | Проход по документации, README в продуктовой фазе, заморозка содержания презентации |
| T − 4 ч | Запись резервного демо, прогон защиты с таймером |
| T − 2 ч | Чек-лист платформы, вычистка истории, запуск из чистого клона |
| T − 1 ч | Отправлено; дальше — запас |

## Организация и ресурсы — раздел «Формулировка задания»

Организаторы не дают ни API, ни MCP-серверов, ни данных Островка; доступов и моделей от них нет.
Состава команды, железа и мероприятий страница трека не перечисляет.
