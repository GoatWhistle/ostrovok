# API

> HTTP API бэкенда Factmap: 25 операций под префиксом `/api/v1`. Контракт записан в
> [`docs/api/openapi.yaml`](api/openapi.yaml); контрактный тест падает, если набор операций
> бэкенда и контракта расходится в любую сторону. Ошибка у всего API одна по форме: машинный `code`
> и `message` для логов.

**Читайте, если** вы интегрируетесь с решением или проверяете, что отдаёт бэкенд · **Связано:**
[архитектура](architecture.md) · [запуск](running.md) · [ограничения](limitations.md)

---

## Где спецификация?

| Что | Где |
|---|---|
| Swagger на запущенном стенде | http://localhost:8000/docs |
| OpenAPI JSON, который FastAPI строит из кода | http://localhost:8000/openapi.json |
| Контракт в репозитории | [`docs/api/openapi.yaml`](api/openapi.yaml) |
| Типы фронтенда | `frontend/src/shared/api/schema.gen.ts` |

Типы фронтенда пересобирает `cd frontend && npm run api:types` через `openapi-typescript@7.13.0`.
Источник берётся из `API_SCHEMA_URL`, по умолчанию `http://localhost:8000/openapi.json`. Текущий
`schema.gen.ts` собран из `docs/api/openapi.yaml`:
`API_SCHEMA_URL=$PWD/../docs/api/openapi.yaml npm run api:types`.

Связь контракта и кода проверяют `tests/contract/` (`cd backend && uv run pytest tests/contract`):

| Тест | Что падает |
|---|---|
| `test_contract_file_is_a_valid_openapi_document` | Контракт перестал быть валидным OpenAPI |
| `test_every_documented_operation_is_served` | Пары метод и путь бэкенда и контракта не совпали; ожидается 25 |
| `test_health_matches_the_contract`, `test_characteristics_match_the_contract` | Ответ `/health` или `/characteristics` не совпал со схемой контракта |
| `test_hotelier.py` | Ответы очереди вопросов, ответа отельера, подтверждения, исправления, факта с историей и их ошибки не совпали со схемами |

Сравнение, места и каталог карты сверяются своими файлами в `tests/contract/`. Остальные ответы со
схемами автоматически не сверяются.

## Как устроены вход и права?

Входа нет: прототип работает в одном рабочем пространстве без регистрации, это же записано в
[ограничениях](limitations.md#нет-входа-и-прав-доступа).

| Что | Как |
|---|---|
| Вход | Нет; ни один метод не требует заголовка авторизации |
| Роли | Нет; страница отельера открывается по адресу без проверки, ответить или исправить факт может любой |
| Диалог | Открывается любым, кто знает его UUID; идентификатор хранится в браузере |
| Ключи внешних сервисов | В ответы и сообщения об ошибках не попадают (`test_the_key_never_appears_in_a_failure_message`) |

## Как выглядит ошибка?

Тело ошибки одно на весь API (`backend/src/hotel_agent/interfaces/http/errors.py`):

```json
{
  "code": "not_found",
  "message": "Hotel not found"
}
```

`code` машинный: фронтенд показывает текст из своих словарей по ключу `errors:api.<code>`, а при его
отсутствии общий текст по виду ошибки. `message` написан по-английски для логов и разработчиков и в
интерфейс не попадает. Для ошибок 5xx в `message` уходит общий текст класса ошибки, а подробности
пишутся только в лог.

| `code` | Статус | Когда |
|---|---|---|
| `validation_error` | 422 | Запрос не прошёл проверку схемы; `message` перечисляет поля |
| `invalid_query` | 422 | Пустой запрос или сообщение; выезд не позже заезда, больше 30 ночей, заезд в прошлом или дальше 730 дней |
| `unknown_characteristic` | 422 | Характеристики нет в реестре |
| `not_found` | 404 | Нет отеля, диалога, факта или тайла; так же отвечает любой путь, которого нет в роутерах |
| `model_failure` | 503 | Языковая модель не ответила за `LLM_TIMEOUT_S` после одного повтора, вернула HTTP-ошибку или ответ не по схеме |
| `invalid_registry` | 500 | Реестр характеристик не читается |
| `internal_error` | 500 | Любая другая ошибка |

## Какие есть разделы?

### Служебные и справочные

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/health` | Проверка здоровья для Compose; возвращает `status` и имя провайдера модели |
| GET | `/api/v1/characteristics` | Реестр характеристик из `characteristics/` |
| GET | `/api/v1/regions` | Загруженные регионы и стартовый вид карты |

### Поиск и диалог

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/search` | Разовый поиск по тексту запроса без истории; `limit` от 1 до 100, по умолчанию 20 |
| POST | `/api/v1/chat/messages` | Сообщение в диалог: новый или продолжение по `conversation_id` |
| GET | `/api/v1/chat/conversations/{conversation_id}` | История диалога и заново рассчитанная выдача |

`POST /api/v1/chat/messages` принимает сообщение до 2000 символов, необязательный
`conversation_id`, регион, выбранный отель и язык `ru` или `en`. Ответ содержит историю, текущий
полный запрос и результаты поиска. Сервер хранит историю в PostgreSQL. При продолжении диалога
живая модель собирает актуальный запрос из предыдущего и нового сообщения; офлайн-разбор
склеивает их через точку с запятой. Поиск проверяет факты из базы и ищет объекты рядом по текущему
запросу. Модель не задаёт значения фактов.

Если модель нашла противоречие, город отсутствует или город не найден в данных, поиск не
запускается, а помощник просит уточнить запрос. Сообщение, на котором модель не ответила,
не сохраняется.

`GET /api/v1/chat/conversations/{conversation_id}` возвращает сохранённый снимок выдачи.
Ответ сообщает число показанных кандидатов, максимум 20, а не общее количество подходящих отелей.

### Отели

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/hotels/{hotel_id}` | Карточка: активные факты с источниками и массив номеров |
| GET | `/api/v1/hotels/{hotel_id}/offers` | Предложения поставщика на даты и состав гостей |
| GET | `/api/v1/hotels/{hotel_id}/details` | Сведения отеля у поставщика без дат: фотографии, факты, категории номеров |
| GET | `/api/v1/hotels/{hotel_id}/scene` | Здание отеля, фасады и соседние здания в радиусе `context_radius_m` (по умолчанию 250, не больше 500 м) |
| GET | `/api/v1/hotels/{hotel_id}/facts/{fact_id}` | Один факт с источником, цитатами, прежними версиями и связанными противоречиями |

Карточка показывает текущие версии фактов, включая устаревшие и спорные, нерешённые противоречия,
число устаревших фактов и открытых вопросов отельеру. Факт другого отеля по адресу
`/hotels/{другой}/facts/{fact_id}` отвечает `404`, прежние версии остаются доступны по своему id.

Номер в карточке включает вместимость, диапазон этажей, фасады, цену и включённые услуги, если они
известны. В текущем срезе Сочи записей о номерах нет; интерфейс сообщает об отсутствии данных.

`GET /api/v1/hotels/{hotel_id}/offers?check_in=YYYY-MM-DD&check_out=YYYY-MM-DD&adults=2&residency=ru`
запрашивает предложения для выбранного отеля. В бесплатном режиме источник —
[JSON сайта Островка](hotel-data.md#откуда-берутся-номера-фотографии-и-факты-островка), без API-ключа.
`adults` от 1 до 10, `residency` две строчные буквы; сайт Островка поддерживает `ru`.
Даты ограничены ближайшими 730 днями и 30 ночами. Поле `status` различает пять случаев:

| `status` | Когда |
|---|---|
| `provider_unavailable` | Нет настроенного источника; в бесплатном режиме сайт отключён через `OSTROVOK_SITE=off` |
| `hotel_unmapped` | Не найдено единственное подтверждённое соответствие отелю |
| `provider_error` | Источник недоступен, ответ повреждён, поиск неполон или превышено время ожидания |
| `no_offers` | Источник не вернул предложений; доступность неизвестна |
| `available` | Есть хотя бы один тариф |

Поле `details` возвращает сведения отеля из каталога поставщика, подтверждённые по адресу
и координатам: фотографии, факты (этажи, число номеров, звёздность, годы постройки и
реконструкции, запись реестра классифицированных объектов со ссылкой), группы услуг с пометкой
«бесплатно», описание, ближайшие объекты с расстояниями поставщика, оценку гостей, время заезда
Цена относится ко всему проживанию на указанные даты в валюте ответа поставщика; `checked_at`
показывает момент запроса. `floor_number` остаётся `null`, пока отель не подтвердил конкретный этаж.

`GET /api/v1/hotels/{hotel_id}/details` возвращает то же `details` и те же категории номеров
без дат и гостей: карточка показывает фотографии, факты и номера сразу, а цены добавляются
запросом предложений, когда даты и число гостей заданы. `status` принимает четыре значения:
`provider_unavailable`, `hotel_unmapped`, `provider_error` и `available`; `no_offers` здесь
невозможен, потому что о наличии мест этот ответ ничего не говорит. Подтверждённое соответствие
отелю хранится 12 часов, поэтому повторное открытие карточки не ходит в каталог заново.

и выезда, телефон и почту. Отсутствующее поле означает неизвестность. Расстояния в `nearby`
получены от поставщика, а не измерены нами по карте. Если цены не пришли, `details` и
`room_groups` всё равно заполняются, а `rates_complete` остаётся `false`.

Тарифы не доказывают возможность бронирования без проверки на шаге prebook, которого в продукте нет.

сбое Open-Meteo `reason` равен `weather_unavailable`.

### Отельер

| Метод | Путь | Что делает | Ошибки |
|---|---|---|---|
| GET | `/api/v1/hotelier/{hotel_id}/overview` | Сводка кабинета: покрытие, непрочитанные оповещения, попадания в выдачу, очередь вопросов, споры, истекающие значения, состояние каждой характеристики и один следующий шаг | `404` нет отеля |
| GET | `/api/v1/hotelier/{hotel_id}/questions` | Очередь вопросов отелю: причина, статус, дата; `?status=open` оставляет только открытые | `404` нет отеля, `422` неизвестный статус |
| GET | `/api/v1/hotelier/{hotel_id}/notifications` | Лента оповещений, новые сверху; `unread_only`, `cursor`, `limit` | `404` нет отеля, `422` размер страницы вне 1–100 или сломанный курсор |
| POST | `/api/v1/hotelier/{hotel_id}/notifications/read` | Отмечает прочитанными указанные оповещения; без тела — все непрочитанные, пустой массив `ids` — ничего | `404` нет отеля, `422` лишнее поле |
| POST | `/api/v1/hotelier/{hotel_id}/facts` | Отельер сам называет значение характеристики, о которой его не спрашивали; текст раскладывается по полям с цитатой | `404` нет отеля, `422` характеристика не из реестра, не уровня отеля, пустой текст или значение не распознано, `503` модель не ответила |
| POST | `/api/v1/hotelier/{hotel_id}/answers` | Один свободный текст против всех открытых вопросов отеля | `404` нет отеля, `422` пустой текст или нет открытых вопросов, `503` модель не ответила |
| POST | `/api/v1/hotelier/questions/{question_id}/answer` | Свободный ответ раскладывается на поля с цитатами и становится фактом | `404`, `422` пустой ответ или вопрос уже закрыт, `503` модель не ответила |
| POST | `/api/v1/facts/{fact_id}/confirm` | Отельер подтверждает текущий факт | `404`, `422` для `superseded` и `computing` |
| POST | `/api/v1/facts/{fact_id}/correct` | Отельер задаёт новое значение; создаётся новая версия, старая получает `superseded` | `404`, `422` значение не того типа, отрицательное число, лишнее поле объекта, прежняя версия |

Вопросы создаёт команда `plan-questions` по реестру: для характеристик уровня отеля с
`ask_hotelier_if_missing: true`, у которых в базе нет текущего факта. Вопрос заводится там, где
незнание уже помешало ответить на живой запрос: по снимкам поиска считается, сколько раз
характеристику спрашивали у этого отеля и получили `unknown`. Пока таких запросов нет, ставится
ограниченная стартовая очередь (`--cold-start`, по умолчанию 20 вопросов), чтобы кабинет не был
пустым на свежей базе. Повторный запуск новых вопросов не добавляет.

Накопленную очередь разбирает `prune-questions`: открытые вопросы, которых не спрашивал ни один
живой запрос, уходят в `skipped`, а отложенные, на которые спрос появился, возвращаются в работу с
оповещением. Отвеченные вопросы команда не трогает. Без записи она только печатает числа; замер по
стенду — в [доказательствах](evidence.md#очередь-вопросов-отельеру-против-реального-спроса-28-октября-2026).

Очередь в сводке упорядочена по весу: причина вопроса, число заблокированных запросов, вес
характеристики в реестре и возраст вопроса. Поле `next_action` называет один шаг: сначала спорное
значение, затем самый весомый вопрос, затем подтверждение истекающего значения отельера.

#### Оповещения

Лента отвечает структурой, а не текстом: вид события в `kind`, срочность в `severity`
(`action` — нужно действие отельера, `info` — к сведению), числа и ключи в `payload`. Фразу
собирает клиент по словарю; название характеристики и текст вопроса приходят готовыми полями.

| `kind` | Когда появляется | `severity` |
|---|---|---|
| `question_opened` | Запланирован вопрос отелю | `action` |
| `answer_needs_detail` | Из ответа не удалось извлечь ни одного поля, вопрос остался открытым | `action` |
| `answer_accepted` | Ответ разложен по полям и стал фактом | `info` |
| `conflict_opened` | Записано противоречие без решения | `action` |
| `conflict_resolved` | Противоречие закрыто правилом или ответом отельера | `info` |
| `fact_changed` | Перепроверка дала другое значение; `action`, если прежнее значение подтверждал отельер | `info` или `action` |
| `fact_expiring` | До конца срока годности меньше двух недель; `action` для значений от отельера | `info` или `action` |
| `search_demand` | За окно наблюдения незнание характеристики помешало живым запросам | `action` |

Одно событие даёт одно оповещение: ключ дедупликации собирается из вида события и ссылок, поэтому
повторный обход ничего не дублирует. У `search_demand` в ключ входит дата, так что напоминание
повторяется не чаще раза в сутки. Оповещения `question_opened`, `answer_*` и `conflict_*` пишутся
в той же транзакции, что и само событие; `fact_expiring` и `search_demand` ставит обход
`make notify-hoteliers`.

Отельеру не обязательно ждать вопроса: `POST /hotelier/{hotel_id}/facts` принимает ключ характеристики и свободный текст. Значение так же берётся из разбора по полям с цитатой, источник — `hotelier`, метод — `hotelier_statement@1`. Характеристика должна быть из реестра и уровня отеля: для номера и фасада нужен свой субъект, поэтому такой запрос отклоняется.

Модель только разбирает ответ на поля реестра и цитирует фразу; значение проверяется по типу
характеристики. Если поле не распознано, вопрос остаётся открытым, текст ответа сохраняется, а в
ответе приходит `follow_up`. Офлайн-разбор понимает фразы из реестра и короткие «да» и «нет».

Ответ отельера побеждает расчёт по правилу `hotelier > fresh_computed > osm_tag > stale_computed`.
Совпадающие значения закрывают прежнюю версию без противоречия. Два разных ответа отельера остаются
спорными, пока один из них не подтвердят или не исправят; тогда противоречие получает
`resolved_by_hotelier`. Повторное подтверждение возвращает тот же факт без новой версии.
Одновременные ответы на один вопрос дают один факт, второй запрос получает `422`.

## Как меняется контракт?

Сначала правится `docs/api/openapi.yaml`, затем код: путь без записи в контракте или запись без
обработчика роняет `test_every_documented_operation_is_served`. Несовместимое изменение выкатывается в три шага:
фронтенд понимает обе формы, бэкенд переходит на новую, старая форма удаляется. Типы фронтенда
пересобираются в том же изменении, где меняется контракт.
