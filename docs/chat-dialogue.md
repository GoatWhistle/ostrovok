# Консультации и поиск в чате

Сообщение сначала проходит маршрутизацию намерения. Модель получает текущую реплику, последние восемь сообщений, предыдущие поисковые условия и, если отель выбран, ограниченные сведения из его карточки. В рабочем приложении передаётся также текущее время. Один структурированный ответ определяет режим и содержит либо поисковый запрос, либо текст консультации.

| Режим | Когда используется | Действие |
|---|---|---|
| `consult` | Приветствие, благодарность, вопрос о поездке или условиях проживания | Ответить, сохранив прежнюю выдачу и условия поиска |
| `hotel` | Вопрос о выбранном отеле | Ответить по данным его карточки, без запуска подбора |
| `search` | Просьба найти отели, заменить варианты или изменить условия подборки | Запустить поисковый пайплайн с полным актуальным запросом |

«Когда лучше ехать в Сочи?» — консультация. «Найди отель в Сочи» — поиск. Ответ «Казань» на вопрос поиска о городе продолжает подборку. «А у него есть парковка?» относится к выбранной карточке. «Найди другой отель» запускает поиск даже при выбранном отеле.

При формировании нового поискового запроса модель сохраняет действующие ограничения и заменяет явно изменённые. Консультационные реплики не добавляются в поисковые условия. При неоднозначном намерении или ошибке модели система отвечает уточняющим вопросом и сохраняет текущую выдачу.

Для выбранного отеля используется `GetHotelCard`: название, адрес, координаты, звёзды, до 12 записей номеров, до 24 фактов и сведения поставщика. Передаются общее число записей, источники, даты и ограничения. Прежняя история не служит доказательством свойств текущего отеля. Отсутствующие сведения остаются неизвестными; инвентаризация не подтверждает свободные номера на даты поездки. В этом режиме новые внешние исследования и проверка актуальных цен не выполняются.

У общего разговора без поиска `effective_query` и `search` равны null. Консультация после поиска сохраняет оба значения. Получение истории чата не вызывает поиск, включая старые чаты без сохранённой выдачи.

Поле `search_message_id` в HTTP-ответе указывает на реплику, создавшую текущую выдачу. Интерфейс сохраняет результаты, выбранный отель и показанный факт после консультации. Кнопки выдачи остаются у поискового ответа. Связь сохраняется внутри существующего JSON-снимка поиска; новые миграции для маршрутизации не нужны. OpenAPI и сгенерированные типы фронтенда обновлены.

Адаптеры Anthropic и OpenAI-compatible используют общий структурированный протокол. Детерминированный режим без ключей маршрутизирует сообщения по ограниченным языковым правилам и отвечает по переданным сведениям; его ответы проще ответов облачной модели.

Проверки охватывают консультации, явный поиск, продолжение после уточнения города, смену выбранной карточки, недоступный отель, отказ модели, сохранение истории и состояния карты. Через HTTP и изолированный PostgreSQL проверена цепочка «приветствие → поиск → консультация → вопрос об отеле → открытие истории»: поиск вызывается один раз. Семантическое качество облачной маршрутизации в живом диалоге отдельно не проверялось. При реализации платная модель не вызывалась и рабочий стенд не перезапускался.
